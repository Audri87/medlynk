# ADR-SA-009 — Persistence Technology Policy

**Document ID**: ADR-SA-009
**Title**: Persistence Technology Policy — DBAL over ORM, Direct Mapping, No Projection Row
**Status**: Approved

---

## Purpose

ADR-SA-007 established *what* the persistence responsibilities are and *who* owns them.

This document establishes *how* those responsibilities are implemented in the MedLink
runtime — specifically, which persistence technology is used at each layer and why, what
problems that choice solves, and which rules may never be violated.

This document is the normative technology complement to ADR-SA-007.

---

## Context

MedLink is built on:

- DDD — Domain objects are pure PHP, without infrastructure coupling
- Hexagonal Architecture — the Domain and Application layers are technology-agnostic
- CQRS — Write and Read paths are structurally separated
- PostgreSQL 17 — the chosen persistence store

The Symfony ecosystem provides two persistence tools:

| Tool | Nature |
|---|---|
| Doctrine ORM | Object-Relational Mapper — maps PHP objects to tables via a managed lifecycle |
| Doctrine DBAL | Database Abstraction Layer — provides typed SQL execution over a connection |

Both tools are available. This document specifies which tool is used at each layer and
provides the complete rationale.

---

## Problem

### P-001 — ORM and Persistence Ignorance Are Incompatible

Doctrine ORM requires one of the following to map an object to a table:

- PHP attributes (`#[ORM\Entity]`, `#[ORM\Column]`) embedded in the class
- External XML or YAML mapping files that reference the class structure

In either case, the ORM maintains a managed lifecycle for each mapped object:
identity map, Unit of Work, lazy loading, proxy generation, change tracking.

If Aggregate Roots are mapped via Doctrine ORM:
- The Domain layer either carries ORM attributes (violating ADR-SA-007 D-009) or is
  structured to satisfy ORM conventions (violating ADR-SA-007 D-009 by proxy).
- The ORM's Unit of Work introduces implicit change tracking that runs parallel to the
  explicit transaction model defined in ADR-SA-007 D-003.
- Proxy classes generated by the ORM replace the actual domain objects during retrieval,
  introducing infrastructure behaviour into the Domain layer at runtime.

There is no configuration of Doctrine ORM that maps Aggregate Roots without coupling the
class design to ORM conventions. The incompatibility is structural, not configurational.

### P-002 — ORM Does Not Support Idempotent Projection Writes

Projection Handlers must be idempotent. When a Domain Event is replayed — during a
rebuild, after a failure, or during a migration — the Projection Handler must produce the
same result regardless of how many times it executes.

Idempotent writes in PostgreSQL are implemented via:

```sql
INSERT INTO patient_timeline (id, ...)
VALUES (...)
ON CONFLICT (id) DO UPDATE SET ... = EXCLUDED.
```

Doctrine ORM does not support `INSERT ... ON CONFLICT DO UPDATE` natively. Its `persist`
and `flush` cycle performs a `SELECT` to determine whether to issue an `INSERT` or an
`UPDATE`. Under concurrent execution or replay, this produces race conditions and
non-idempotent behaviour.

Implementing idempotent Projection Handlers with Doctrine ORM requires bypassing the ORM
and using DBAL directly. If DBAL is required for correctness, the ORM layer adds overhead
without architectural benefit.

### P-003 — ORM Intermediate Classes Violate the Model Existence Principle

If Doctrine ORM is used for the Read path (ViewRepository), it requires a mapped entity
class — a `ProjectionRow` — to serve as the ORM-managed in-memory representation of a
database row.

This class:
- Has the same structure as the View DTO it will be converted to
- Carries no distinct behaviour
- Exists solely because the ORM requires an entity class to perform mapping
- Does not pass the Existence Test defined in ADR-SA-008

Creating a `ProjectionRow` class to satisfy ORM conventions introduces a mapping step
(`ProjectionRow → View DTO`) that adds maintenance surface without architectural value.

### P-004 — ORM Lifecycle Creates Unexpected Behaviour in Event Handlers

Projection Handlers execute in the `event.bus` context — after the `command.bus`
transaction has committed. If Doctrine ORM is used for Projection writes, the
EntityManager's Unit of Work carries state from the Command Handler transaction.

This creates two risks:
- An EntityManager that has accumulated managed entities from the Write Side may
  flush unexpected changes when a Projection Handler triggers a `flush()`.
- A Projection Handler that fails mid-execution leaves the EntityManager in a dirty
  state. Subsequent Handlers executing on the same PHP-FPM worker may encounter
  inconsistent EntityManager state.

With DBAL, each `executeStatement()` is stateless. There is no Unit of Work to contaminate
across Handler boundaries.

## Decisions

### D-001 — Domain Layer: Zero Persistence Dependency

The Domain layer SHALL NOT depend on any persistence technology.

This includes:
- Doctrine ORM (`#[ORM\Entity]`, `#[ORM\Column]`, `#[ORM\Id]`, and all other ORM attributes)
- Doctrine DBAL (`Connection`, `QueryBuilder`, `Result`, or any DBAL type)
- Any framework-specific persistence interface, base class, or annotation

Deptrac enforces this rule. The `Clinical.Domain` layer has no allowed dependency on
`External` (Symfony, Doctrine, API Platform).

**Rationale:** The Domain Model embodies certified domain knowledge. Its correctness must
be verifiable without persistence infrastructure. Its lifetime must exceed any persistence
technology choice. ADR-SA-007 D-009.

**Violation example:**
```php
// PROHIBITED — ORM annotation in the Domain layer
#[ORM\Entity]
final class ClinicalContribution
```

### D-002 — Application Layer: Zero Persistence Dependency

The Application layer — Command Handlers, Query Handlers, Application Ports — SHALL NOT
depend on any persistence technology.

Application Ports define contracts using only Domain types and Application DTOs.
Application Handlers depend only on Port interfaces, never on Infrastructure adapters or
persistence types.

**Rationale:** The Application layer is the use case boundary. Its independence from
persistence technology enables isolated use case testing without database infrastructure.
ADR-SA-007 D-009.

**Violation example:**
```php
// PROHIBITED — DBAL import in an Application Port
use Doctrine\DBAL\Connection;

interface ClinicalContributionRepositoryPort
{
    public function save(ClinicalContribution $contribution, Connection $connection): void;
}
```

### D-003 — Write Side: DBAL with Explicit SQL

The Write Side — Aggregate Repository implementations — SHALL use Doctrine DBAL exclusively.

SQL statements SHALL be explicit. No query builder abstraction is required, but DBAL's
`QueryBuilder` is permitted when it improves clarity without obscuring the query intent.

Each Repository implementation is responsible for:
- Translating Aggregate state to a DBAL-compatible parameter set
- Executing the `INSERT` or `UPDATE`
- Translating retrieved rows back to Aggregate state

Doctrine Reflection (`ReflectionClass`, `ReflectionProperty`) is the authorised mechanism
for reading private Aggregate state without adding accessors. A dedicated Mapper class is
permitted when the translation logic is complex enough to warrant isolated testing
(ADR-SA-008 D-006).

**Rationale:** DBAL provides complete control over SQL execution and transactions.
It imposes no lifecycle on the objects it persists. It does not require entity classes.
It allows the Aggregate to be a pure domain object (ADR-SA-007 D-006, D-009).

**Example:**
```php
// Justified — DBAL write in Repository implementation
$this->connection->executeStatement(
    'UPDATE clinical_contributions
     SET status = :status, updated_at = :updatedAt
     WHERE id = :id',
    [
        'id'        => $contribution->id()->value(),
        'status'    => $contribution->status()->value,
        'updatedAt' => new \DateTimeImmutable('now', new \DateTimeZone('UTC')),
    ],
    [
        'updatedAt' => Types::DATETIME_IMMUTABLE,
    ]
);
```

### D-004 — Projection Writes: DBAL with PostgreSQL UPSERT

Projection Handler implementations SHALL use Doctrine DBAL exclusively.

Every Projection write SHALL use PostgreSQL `INSERT ... ON CONFLICT DO UPDATE` (UPSERT).

**Idempotence is not optional.** A Projection Handler that is not idempotent is incorrect.

**Rationale:** Domain Events may be replayed. Projection Handlers execute after transaction
commit on the `event.bus`. Idempotence prevents data corruption during replay and
protects against at-least-once delivery semantics. DBAL is the only tool that supports
native UPSERT in this stack (P-002).

**Example:**
```php
// Justified — idempotent UPSERT in Projection Handler
$this->connection->executeStatement(
    'INSERT INTO patient_timeline (id, care_record_id, clinical_text, status, occurred_at)
     VALUES (:id, :careRecordId, :clinicalText, :status, :occurredAt)
     ON CONFLICT (id) DO UPDATE SET
         clinical_text = EXCLUDED.clinical_text,
         status        = EXCLUDED.status',
    [...],
);
```

**Violation example:**
```php
// PROHIBITED — non-idempotent Projection write
$this->connection->executeStatement(
    'INSERT INTO patient_timeline (...) VALUES (...)'
    // no ON CONFLICT clause — will fail on replay
);
```

### D-005 — Read Side: DBAL with Direct array → View DTO Mapping

ViewRepository implementations SHALL use Doctrine DBAL exclusively.

The mapping path SHALL be:

```
DBAL result (array) → View DTO (Application contract)
```

No intermediate class exists between the DBAL result and the View DTO.

The ViewRepository implementation performs the mapping inline. If the mapping exceeds five
field assignments, a private mapping method within the same class is permitted. A
dedicated Mapper class is permitted only when the mapping is reused across multiple
ViewRepositories — in which case it must pass the Existence Test (ADR-SA-008 D-006).

**Rationale:** A `ProjectionRow` class fails the Existence Test (ADR-SA-008 D-003, D-004).
The DBAL result `array` carries no forbidden dependency. The mapping is mechanical,
explicit, and testable directly through the ViewRepository integration test. No
intermediate class is necessary or permitted (P-003).

**Example:**
```php
// Justified — direct DBAL → DTO mapping
public function findByPatient(CareRecordId $careRecordId): PatientTimelineView
{
    $rows = $this->connection->fetchAllAssociative(
        'SELECT id, clinical_text, status, occurred_at
         FROM patient_timeline
         WHERE care_record_id = :careRecordId
         ORDER BY occurred_at DESC',
        ['careRecordId' => $careRecordId->value()],
    );

    $entries = array_map(
        fn(array $row) => new PatientTimelineEntry(
            clinicalContributionId: $row['id'],
            clinicalText: $row['clinical_text'],
            status: ContributionStatus::from($row['status']),
            occurredAt: new \DateTimeImmutable($row['occurred_at']),
        ),
        $rows,
    );

    return new PatientTimelineView($careRecordId->value(), $entries);
}
```

**Violation example:**
```php
// PROHIBITED — intermediate class between DBAL and DTO
$rows = ...; // DBAL result
$projectionRows = array_map(fn($r) => PatientTimelineRow::fromArray($r), $rows); // ← not justified
$entries = array_map(fn($r) => $r->toEntry(), $projectionRows);                  // ← extra mapping step
```

### D-006 — Doctrine ORM Is Not Used

Doctrine ORM SHALL NOT be used anywhere in the MedLink persistence stack.

This prohibition covers:
- Aggregate persistence (Write Side)
- Projection writes (Projection Handlers)
- Read Model reads (ViewRepositories)
- Any new persistence context introduced in the future

**If a future use case appears to require Doctrine ORM**, an Architecture Decision Record
must be written before implementation begins. That ADR must demonstrate:
1. The requirement cannot be met by DBAL alone.
2. The ORM usage does not introduce a managed lifecycle on Domain objects.
3. The ORM usage does not create an intermediate class that fails the Existence Test.
4. Idempotent writes remain achievable.

Absent a new approved ADR, the prohibition stands.

**Rationale:** The combination of P-001, P-002, P-003, and P-004 makes Doctrine ORM
incompatible with the persistence guarantees required by MedLink's architecture. DBAL
provides everything MedLink needs without the lifecycle, annotation, and idempotence
constraints that ORM imposes.

## Problems This Approach Solves

### S-001 — Persistence Ignorance Is Guaranteed

No Aggregate, Value Object, or Domain Event carries any persistence knowledge. The Domain
layer is testable in complete isolation. Replacing PostgreSQL with another storage
technology requires only Infrastructure layer changes.

### S-002 — Idempotent Projections Are Structurally Guaranteed

Every Projection write uses UPSERT. Replay, failure recovery, and migration replays
produce identical outcomes regardless of execution count. The idempotence guarantee is
in the SQL, not in application-level logic.

### S-003 — No Entity Drift

When Doctrine ORM entities exist in the Infrastructure layer, there is a persistent risk
that business logic, validation annotations, or lifecycle callbacks accumulate on those
classes over time — transforming them into de-facto domain objects (ADR-SA-008, §Risk 4).

With no ORM entities in the codebase, this drift is structurally impossible. There is no
class to accumulate business behaviour in.

### S-004 — Explicit, Auditable SQL

Every database operation performed by MedLink is a readable SQL statement in a PHP file.
There are no hidden queries generated by ORM lazy loading, no proxy method calls, no
implicit JOIN traversals. Debugging a persistence issue requires reading one file.

### S-005 — Stateless Handler Execution

Projection Handlers execute on the `event.bus` without EntityManager state from the
Command Handler transaction. Each DBAL `executeStatement()` is atomic and independent.
There is no Unit of Work to contaminate across Handler boundaries (P-004).

### S-006 — Minimal Maintenance Surface

Adding a field costs:

| Step | Action |
|---|---|
| Domain Event | +1 property |
| Migration | +1 column in SQL |
| Projection Handler | +1 DBAL parameter |
| ViewRepository | +1 field in the mapping |
| View DTO | +1 constructor property |

Five mechanical changes. No Projection Row class, no ORM entity, no additional mapper.

## Limits of This Approach

### L-001 — Manual SQL for All Operations

DBAL does not generate SQL. Every query, insert, update, and upsert is written by hand.
For simple operations, this is acceptable overhead. For complex reporting queries with
multiple joins and dynamic filters, the SQL can become verbose.

**Mitigation:** The `QueryBuilder` is permitted where it reduces verbosity without
obscuring intent. Complex reporting surfaces may be addressed by a dedicated Reporting
layer in a future ADR.

### L-002 — No Auto-Generated Migrations

Doctrine ORM can generate migration files from entity annotations. With DBAL, every
migration is written manually.

**Mitigation:** Manual migrations are more explicit and less prone to silent errors than
auto-generated ones. They must be reviewed in every PR. The discipline of reviewing
migrations is a safety property, not a cost.

### L-003 — No Transparent Relation Navigation

ORM lazy loading allows callers to navigate object relationships without explicit SQL.
With DBAL, every join must be explicit. Retrieving a `PatientTimelineView` with its
entries requires a JOIN or two separate queries written explicitly.

**Mitigation:** Explicit SQL is preferable to transparent relation navigation for Read
Models, where query shapes are dictated by display requirements, not object graphs. Joins
are readable and debuggable. Lazy loading is not.

### L-004 — Developer Onboarding Curve

Developers experienced with Doctrine ORM patterns may expect entity classes, repositories
with `find()` and `findBy()`, and automatic schema management.

**Mitigation:** This document and ADR-SA-008 provide explicit rationale. Onboarding
documentation must reference these ADRs. The patterns in this stack are simpler than ORM
in practice; the learning curve is front-loaded.

## Rules That May Never Be Violated

These are non-negotiable invariants. Violating any of them requires an approved ADR before
implementation.

| Rule | Scope | Consequence of Violation |
|---|---|---|
| **R-001** | The Domain layer has zero Doctrine dependency (ORM or DBAL) | Deptrac violation; PR rejected |
| **R-002** | The Application layer has zero persistence technology dependency | Deptrac violation; PR rejected |
| **R-003** | Aggregate Repositories use DBAL only | Architecture violation; requires ADR |
| **R-004** | Projection Handlers use DBAL + UPSERT | Loss of idempotence guarantee; data corruption on replay |
| **R-005** | ViewRepositories use DBAL with direct array → DTO mapping | Architecture violation; requires ADR |
| **R-006** | Projection Row classes do not exist | Existence Test failure (ADR-SA-008); PR rejected |
| **R-007** | Doctrine ORM is not used | Architecture violation; requires ADR |
| **R-008** | View DTOs are immutable and carry zero behaviour | Application contract contamination |
| **R-009** | Every Projection write is idempotent via ON CONFLICT | Non-idempotent Projection is architecturally incorrect |
| **R-010** | No persistence technology appears above the Infrastructure boundary | Hexagonal Architecture violation |

## Technology Summary

| Layer | Technology | SQL | Migration |
|---|---|---|---|
| Domain | None | None | None |
| Application | None | None | None |
| Write Side — Aggregate Repository | Doctrine DBAL | Explicit | Manual |
| Projection Layer — Projection Handler | Doctrine DBAL | Explicit UPSERT | Manual |
| Read Side — ViewRepository | Doctrine DBAL | Explicit SELECT | Manual |

Doctrine ORM: not present in any layer.
